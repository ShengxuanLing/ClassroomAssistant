# TASK-KM-PREMIUM-REDESIGN
# Loomind 知识地图：产品级重设计与完整实施计划

**优先级：P0 / 核心产品体验**

**任务性质：设计研究 → 产品方案 → 交互原型 → 视觉系统 → 正式实施 → 真实验收**

**授权范围：** 允许重新设计整个 Knowledge Map 前端，评估并引入成熟的开源 UI、图布局、动画、搜索、虚拟化和交互方案。Token、开发时间和合理的依赖成本不是本任务的主要限制。优先保证最终产品质量。

**重要前提：** 上一次 Knowledge Map V2 已经回滚。本任务必须以当前仓库实际状态为准，不得假设之前的 V2 代码、文件、测试或架构仍然存在。

---

## 一、任务目标

我要的不是一个能够显示节点的关系图，也不是一个普通的思维导图模板。

我要把 Loomind 的知识地图做成一个真正成熟的课程学习产品：

- 视觉设计精致，有明确的设计语言和产品辨识度。
- 第一次进入页面就能理解课程的知识结构。
- 知识点数量从几十增长到几百、上千时，仍然能有效导航。
- AI 能够融合多个课程材料中的相同知识，而不是把每份材料变成一堆重复卡片。
- 学生可以从课程主题进入知识点，继续阅读概念、例子、关系和原始证据。
- 学生可以从任意一个知识点追溯到相关课堂 PPT、笔记、PDF 和其他材料。
- 搜索不是简单过滤，而是能够定位、解释和串联知识。
- 复杂信息通过渐进式展示、局部聚焦和不同视图来管理，而不是全部挤在一张画布上。
- 交互自然，动画克制，加载和错误状态完整。
- 中文、西班牙语、加泰罗尼亚语保持一致的产品质量。
- 所有视觉设计必须在真实浏览器中经过检查，而不是只在代码和测试中宣布完成。

**最终判断标准：** 一个第一次使用系统的学生，能在几秒钟内找到感兴趣的课程主题，理解一个知识点，并继续找到它的解释、相关知识、来源材料和证据。

如果只是节点可以拖动、画布可以缩放、测试全部通过，但学生仍然看不懂地图，任务就是失败。

# 二、不可妥协的实施原则

## 2.1 先研究，后设计，再编码

严格遵循：

```text
审计现有项目
    ↓
研究成熟产品与设计资源
    ↓
整理设计证据与可复用方案
    ↓
提出多个产品设计方向
    ↓
选择最佳方向
    ↓
建立设计系统和高保真交互原型
    ↓
使用真实课程数据评审原型
    ↓
确定最终架构
    ↓
正式实现
    ↓
真实浏览器验收
    ↓
性能、可访问性、回归测试
    ↓
产品验收与文档
```

不允许跳过研究和原型阶段，直接修改现有 CSS 或重写 `knowledge.js`。

## 2.2 允许大胆创新

不要因为现有项目比较简单，就限制在现有 UI 模式里。

可以研究并采用：

- 交互式知识地图。
- 层级式课程导航。
- 空间化知识画布。
- 课程知识目录与可视化地图的双视图。
- 聚焦式局部地图。
- 时间线与课程材料的联动。
- 知识关系探索。
- 跨材料知识融合展示。
- 搜索驱动的知识导航。
- 基于内容的动态布局。
- 多视图之间的平滑过渡。
- 适合复杂知识的渐进式展开。
- 能够解释 AI 为什么认为两个概念相同的融合审查界面。

但创新必须服务于学习效率，不能只是炫酷的动画。

## 2.3 研究不等于照搬

成熟产品可以提供：

- 交互模式。
- 信息架构。
- 布局策略。
- 视觉设计参考。
- 可复用的开源组件。
- 可借鉴的动画。
- 可验证的工程实践。

必须检查许可证、依赖、可访问性和现有技术栈兼容性。不能因为一个组件在网站上看起来漂亮，就直接复制其代码或将其用于不允许的场景。

## 2.4 保留后端业务事实

在确认当前代码后，优先保留现有的：

- Canonical Knowledge。
- Knowledge Candidate。
- Merge Proposal。
- Knowledge Relation。
- Material。
- Evidence。
- Knowledge Map API。
- AI 分析流水线。
- 课程和课次管理。
- 材料上传与查看。
- 已有的多语言机制。

除非研究发现确实存在必要的后端缺陷，否则本任务不应重写知识融合算法或改变 API 的语义。

前端可以大胆重构，知识数据不能为了视觉效果被伪造或丢弃。

# 六、第四阶段：先提出三个完整的产品设计方向

在正式编码前，至少提出三个明显不同的设计方案，而不是同一个布局换三套颜色。

每个方案都必须针对真实课程数据展示：

- 初始页面。
- 课程知识结构。
- 知识点详情。
- 跨材料来源。
- 搜索结果。
- 关系探索。
- 小屏或窄窗口。

## 方案 A：Structured Knowledge Atlas

核心思想：课程知识图谱 + 层级目录。

特征：

- 课程作为根。
- Topic 作为一级分区。
- Knowledge 作为核心节点。
- 复杂内容进入详情面板。
- 适合课程整体复习和结构浏览。

## 方案 B：Spatial Learning Canvas

核心思想：高品质空间化知识画布。

特征：

- 无限画布。
- 节点分组。
- 局部展开。
- 柔和的连接线。
- 可拖动的主题分区。
- 搜索后自动定位。
- 强调探索和发现。

但必须解决空间画布的阅读顺序、自动布局、初始视图和大型图导航问题。

## 方案 C：Knowledge Explorer

核心思想：搜索、知识目录、详情阅读和关系探索相结合。

特征：

- 左侧课程导航。
- 中央结构视图。
- 右侧知识详情。
- 支持列表、树和地图之间切换。
- 通过搜索进入具体知识。
- 来源和证据是主要信息，而不是附属信息。

可以在研究后提出更好的第四种方案，但必须说明为什么它更优。

## 6.1 方案评估

建立评分表：

| 维度 | 权重 |
|---|---:|
| 初次使用的可理解性 | 20% |
| 长期学习效率 | 20% |
| 视觉设计质量 | 15% |
| 复杂知识导航 | 15% |
| 跨材料融合体验 | 10% |
| 大图可用性 | 10% |
| 工程可行性和维护性 | 10% |

评分不能代替真实评审。

每个方案必须说明：

- 主要优势。
- 主要缺陷。
- 适合的用户场景。
- 不适合的用户场景。
- 技术风险。
- 预期实施成本。

最终选择一个主方案，并明确哪些其他方案的优点值得吸收。

# 七、第五阶段：建立真正完整的视觉设计系统

不能继续只写一些颜色、圆角和间距，然后直接开始编码。

建立统一的 Design System。

## 7.1 品牌与整体风格

目标：

- Professional。
- Academic。
- Calm。
- Precise。
- Modern。
- Visually distinctive。
- High readability。

避免：

- 过度使用渐变。
- 过度使用玻璃拟态。
- 满屏发光边框。
- 每个节点使用不同颜色。
- 卡片无节制堆叠。
- 全屏动画。
- 只追求截图好看。
- 无意义的装饰性图标。
- 默认所有元素都使用圆角胶囊。
- 所有内容都塞进深色卡片。

不要简单复制 shadcn/ui 默认风格。它可以提供组件基础，但最终产品应有自己的视觉系统。

## 7.2 必须定义的设计 Token

包括：

- Color palette。
- Background layers。
- Surface elevation。
- Typography scale。
- Font weight。
- Line height。
- Spacing scale。
- Border radius。
- Border color。
- Shadow。
- Focus ring。
- Hover state。
- Selected state。
- Disabled state。
- Motion duration。
- Motion easing。
- Z-index。
- Responsive breakpoints。
- Node size。
- Panel width。
- Canvas padding。

使用语义化 Token，而不是在不同组件里反复硬编码颜色。

## 7.3 字体与排版

课程内容包含中文、西班牙语和加泰罗尼亚语。

必须验证：

- 重音符号。
- 特殊字符。
- 长标题。
- 混合语言标题。
- 术语。
- 长段描述。
- 窄屏文字换行。

字体选择以可读性、字符覆盖和项目现有依赖为依据。

## 7.4 图标

使用统一图标系统。

每个图标都应有明确语义。

禁止：

- 同一个操作在不同位置使用不同图标。
- 用装饰性图标代替文字说明。
- 把没有 Tooltip 的纯图标按钮作为主要操作。
- 依赖颜色作为唯一状态提示。

## 7.5 动画

动画必须服务于空间连续性和操作反馈。

可以参考 Transitions.dev、beUI 和 Rare UI 中实际验证过的模式：

- 面板平滑展开。
- 卡片尺寸变化。
- 搜索结果聚焦。
- 详情切换。
- 内容渐入。
- 轻量状态反馈。
- 数字变化。
- 列表与详情之间的过渡。

但不允许：

- 节点每次点击都全图重排。
- 大量节点同时弹跳。
- 长时间阻塞操作的动画。
- 为了动画引入不必要的复杂性。
- 忽略 `prefers-reduced-motion`。

建议将一般交互动画控制在约 120–240ms，复杂布局过渡可以更长，但必须经过实际测试。

# 八、第六阶段：重新设计产品信息架构

知识地图不能只是一张 Canvas。

最终至少需要以下五个互相配合的工作视图。

## 8.1 Overview：课程总览

用户进入课程后首先看到清晰的课程结构。

可能包含：

- 课程名称。
- Topic 数量。
- Canonical Knowledge 数量。
- 已关联材料数量。
- 已有证据数量。
- 待审查的合并建议。
- 最近新增或更新的知识。
- 主要知识主题入口。

不要把 Overview 做成无意义的数据 Dashboard。

所有统计必须来自真实数据。

## 8.2 Map：知识地图

主地图负责：

- 理解整体结构。
- 浏览 Topic。
- 展开知识。
- 发现相关知识。
- 进入局部聚焦。
- 打开详情。
- 导航到来源材料。

地图不是完整正文阅读器。

## 8.3 Explorer：知识探索

适合搜索后查看知识点的上下文。

可以显示：

- 当前知识。
- 上级 Topic。
- 子概念。
- 相关知识。
- 关联材料。
- 证据数量。
- 为什么这些知识相关。

如果存在真实关系证据，可以进一步展示关系类型和来源。

不要虚构 AI 解释或因果关系。

## 8.4 Materials：材料地图

允许从材料反查知识。

例如：

```text
Sessió 03 — Apunts
    ├── Stakeholders
    ├── Project Governance
    └── Project Planning
```

材料必须可点击，能够进入材料详情。

材料和知识点之间必须使用真实关联。

## 8.5 List：知识目录

列表是重要的备用视图，不是调试残余。

必须支持：

- 搜索。
- 排序。
- 筛选。
- 分组。
- 展示来源数量。
- 展示证据数量。
- 打开详情。
- 在地图中定位。
- 显示合并状态。

对于希望快速阅读或不习惯图形界面的学生，列表应该同样好用。

# 九、第七阶段：设计多层次的知识地图，而非单一图形

## 9.1 地图的核心数据语义

目标数据链：

```text
Course
  ↓
Topic
  ↓
Canonical Knowledge
  ↓
Subconcept / Concept（仅在真实数据支持时）
```

辅助关联：

```text
Canonical Knowledge
  ↔ Related Knowledge

Canonical Knowledge
  ↔ Material

Canonical Knowledge
  ↔ Evidence
```

主层级与普通语义关联必须明确区分。

不得把 related-to 自动转换成 parent-child。

不得为了让布局更整齐而制造不存在的知识层级。

## 9.2 必须支持多种视觉模式

研究后选择适当的模式，至少考虑：

### Hierarchy View

适合理解课程结构。

### Topic View

选择一个主题后，只展示该主题及其下属知识。

### Focus View

选择一个知识点后，展示其上下文：

- 上级 Topic。
- 子概念。
- 相关知识。
- 来源材料。

### Relation View

专门探索知识之间的关联。

只在这里使用更丰富的关系边，避免污染默认层级视图。

### Material View

从材料出发浏览其贡献的知识。

### List View

用于精确搜索、批量浏览和快速阅读。

不同模式必须共享同一份知识事实，不得维护彼此不一致的副本。

## 9.3 选择最合适的布局算法

根据真实数据和选型结果决定：

- ELK。
- Dagre。
- D3 Hierarchy。
- 其他成熟布局引擎。
- 自定义布局。

如果使用树布局，必须确保布局依据真实层级。

如果使用关系网络，必须处理边交叉、节点密度和局部聚焦。

不要使用随机坐标或 `index % N` 之类的固定分组方式伪装自动布局。

## 9.4 默认视图必须可读

禁止第一次进入页面就显示所有深层节点。

默认策略应根据实际课程数据和原型测试决定：

- 显示课程概览。
- 显示 Topic。
- 对复杂 Topic 采用折叠或摘要。
- 允许逐步展开。
- 提供清晰的展开状态。
- 在用户聚焦某个主题后，自动调整视口。

不能只通过缩小整个图来适配屏幕。

**完整地图可以很大，但初始视图必须清晰。**

# 十、第八阶段：打造知识节点与详情体验

## 10.1 节点不是缩小版详情页

每个节点只展示当前任务真正需要的信息。

候选内容：

- 标题。
- 所属 Topic。
- 来源材料数量。
- Evidence 数量。
- 子知识数量。
- 重要状态。
- 展开或折叠控件。

根据节点类型设计不同布局。

不要把完整 AI Summary、长段说明、所有 Evidence 全部塞进节点。

## 10.2 视觉层级

至少明确区分：

- Course。
- Topic。
- Canonical Knowledge。
- 子概念。
- 合并建议。
- 语义关联。

但不要给每个节点任意指定颜色。

使用尺寸、排版、间距、边框、背景、图标和位置共同表达层级。

## 10.3 Detail Panel

点击知识后，详情面板至少包括：

1. 标题。
2. 简明摘要。
3. 核心概念。
4. 上级主题。
5. 子概念。
6. 相关知识。
7. 关联材料。
8. Evidence。
9. 原始材料定位信息。
10. 合并状态（如适用）。

详情面板应支持合理的展开、滚动和窄屏布局。

面板内容变化时，不应导致整个地图重新计算布局。

## 10.4 跨材料融合必须成为产品亮点

例如：

```text
Stakeholders
```

详情显示：

```text
Consolidated knowledge

Materials
  Sessió 01 — PPT
  Sessió 03 — Apunts
  Sessió 04 — PDF

Evidence
  5 source passages

Related knowledge
  Project Governance
  Communication Planning
```

以上仅为展示结构的示例，不能把这些示例数据写入真实课程。

实际内容必须来自 API。

用户必须能理解：

- 这个知识点由哪些材料支持。
- 不同材料是否提供了互补信息。
- 当前摘要对应哪些原文。
- 哪些关系来自已有数据。
- 哪些融合仍然需要人工审查。

# 十一、第九阶段：重新设计搜索和导航

搜索是核心入口，而不是普通输入框。

## 11.1 全局搜索

支持搜索：

- Knowledge。
- Topic。
- Material。
- 可检索的概念。
- 可检索的摘要内容（如果现有数据支持）。

搜索结果应显示：

- 标题。
- 类型。
- 所属 Topic。
- 来源数量。
- 简短上下文。
- 是否属于合并候选（如适用）。

## 11.2 搜索后定位

用户选择结果后：

1. 切换到正确视图。
2. 展开必要的父级路径。
3. 定位目标。
4. 高亮目标。
5. 打开详情或提供明确的打开操作。
6. 保留其他节点作为上下文，不应无条件删除所有不匹配节点。

如果过滤模式确实需要隐藏节点，应与搜索导航模式明确区分。

## 11.3 命令面板

研究是否适合引入 Command Palette。

可以支持：

- 搜索知识。
- 切换课程视图。
- 切换地图和列表。
- 打开材料。
- 切换关系显示。
- 聚焦当前知识。
- 展开或折叠主题。

如果采用 `Ctrl/Cmd + K`，必须处理与浏览器、输入框及其他快捷键的冲突。

## 11.4 导航路径

清楚显示：

```text
Course > Topic > Knowledge
```

用户可以随时回到上级。

不要让用户在画布中迷路。

# 十二、第十阶段：合并建议与 AI 解释

合并建议不应直接污染主知识地图。

应当区分：

- 已经确认的 Canonical Knowledge。
- 高置信度候选。
- 需要人工审查的候选。
- 被拒绝的候选。
- 已经合并的历史记录。

具体状态必须以当前后端模型为准。

可以设计一个独立的 Merge Review 工作流：

```text
候选知识 A
    +
候选知识 B
    ↓
对比标题、内容、材料与证据
    ↓
展示相似点与差异
    ↓
显示合并理由及置信度（如果后端提供）
    ↓
接受 / 拒绝 / 暂缓
```

只有在当前后端支持对应操作且确认不会破坏数据完整性时，才实现写操作。

不得把低置信度候选自动合并，也不得为视觉效果隐藏未处理状态。

# 十三、第十一阶段：动画、过渡与微交互

研究 Transitions.dev、beUI、Rare UI 的实际组件与交互。

只采用对本产品有价值的动画：

- 详情面板展开。
- 视图切换。
- 搜索结果定位。
- 节点选择。
- 局部地图展开。
- 卡片尺寸变化。
- 加载完成。
- 通知和操作反馈。
- 关系边显示与隐藏。

必须满足：

1. 动画不会阻塞交互。
2. 用户可以迅速连续操作。
3. 选择节点不会触发整张图无必要地重排。
4. 大量节点不应同时执行昂贵动画。
5. 支持 `prefers-reduced-motion`。
6. 动画失败或被禁用时，功能仍然完整。
7. 关键状态变化不能只靠动画表达。

动画不是本项目的主角。知识导航才是。

# 十四、第十二阶段：技术架构与工程质量

## 14.1 前后端职责

保持：

```text
Backend
  ├── Canonical Knowledge
  ├── Knowledge Relations
  ├── Materials
  ├── Evidence
  └── Knowledge Map Projection
          ↓
Frontend View Model
          ↓
Layout Engine
          ↓
Visible Graph / List
          ↓
Interaction Layer
          ↓
Detail Panel
```

Backend owns semantic truth.

Frontend owns visualization.

## 14.2 建立明确的 View Model

不要让 Graph Renderer 直接依赖整个 API 响应的内部结构。

建立清晰的映射层，至少考虑：

- Course。
- Topics。
- Canonical Knowledge。
- Hierarchy。
- Relations。
- Materials。
- Evidence。
- Merge Proposals。
- Statistics。
- Filters。

节点的 ID、父子关系、来源关系必须保持稳定。

## 14.3 状态管理

区分：

- 服务端业务数据。
- View Model。
- Layout。
- 可见节点。
- 当前选中节点。
- 当前聚焦路径。
- 搜索状态。
- 详情面板状态。
- 视图模式。
- 用户交互状态。

不要把所有状态塞进一个巨大对象，并在每次点击时全部重新计算。

## 14.4 布局缓存

只有在数据、可见节点或布局配置真正变化时才重新布局。

普通节点选择、详情切换和 Hover 不应触发完整布局。

必要时使用布局缓存、Web Worker 或其他合理优化，但必须通过测量证明其价值。

## 14.5 错误处理

必须覆盖：

- API 失败。
- 空课程。
- 没有 Topic。
- 没有 Knowledge。
- 没有 Evidence。
- 材料已删除或不可用。
- 数据关系不完整。
- 搜索没有结果。
- 布局失败。
- 大图加载缓慢。
- 切换课程时的竞态。
- 组件重复挂载。
- 旧请求覆盖新请求。

不能让一个异常使整个课程页面变成空白。

# 十六、第十四阶段：性能目标

不能只用 20 个节点证明性能。

至少使用可重复的数据集测试：

- 50 个节点。
- 100 个节点。
- 200 个节点。
- 500 个节点。
- 1000 个节点。

其中 500 和 1000 个节点的目标是验证架构扩展能力；不要求在没有真实需求时强行将所有节点同时显示。

测试：

- 初次加载。
- 首屏显示。
- 展开。
- 折叠。
- 搜索。
- 聚焦。
- 切换视图。
- 打开详情。
- 关系显示。
- 拖动。
- 缩放。
- 切换课程。

建议目标：

- 一般交互尽可能保持在 100ms 以内给出可见反馈。
- 对复杂布局提供明确的处理中状态。
- 在代表性桌面设备上，50–200 个可见节点应保持流畅操作。
- 500–1000 个节点通过折叠、局部视图、虚拟化或其他合适方案保持可操作。
- 不得用隐藏节点或空白演示数据制造性能通过的假象。

所有性能目标应记录测试环境、数据规模、测量方法和结果。

- 是否只借鉴设计模式。

优先使用：

- 有明确许可证的开源组件。
- 官方文档。
- 可维护的依赖。
- 能够在本地定制的组件。

如果某个设计网站包含付费组件或受限源码：

- 可以研究公开演示。
- 可以从交互中获得启发。
- 不得未经授权复制其专有代码。
- 不得将 Pro-only 组件当成免费可用资源。

对于 shadcn/ui 一类可将组件源代码纳入项目的方案，要确认其官方安装方式、依赖、样式系统和现有工程兼容性。

不能因为某个 UI 组件很漂亮，就把整个技术栈迁移到不必要的框架。

# 二十四、最终验收标准

## A. 产品体验

- 初次使用能够理解课程结构。
- 默认视图不是拥挤的节点集合。
- 用户能快速找到目标知识。
- 用户能从全局进入局部。
- 用户能从知识进入材料。
- 用户能从材料反查知识。
- 用户能理解知识之间的真实关联。
- 复杂信息采用渐进式展示。
- 地图和列表都可以完成实际任务。

## B. 视觉质量

- 设计系统统一。
- 文字清晰可读。
- 视觉层级明确。
- 节点没有明显重叠。
- 没有无意义的装饰。
- 动画克制。
- 空状态、错误状态和加载状态完整。
- 窄屏布局合理。
- 多语言排版正常。

## C. 数据正确性

- 不丢失现有知识。
- 不丢失材料。
- 不丢失 Evidence。
- 不伪造知识层级。
- 不把普通关系转换成父子关系。
- 不把 Merge Proposal 当成已确认知识。
- 所有来源都能追溯。
- 多个视图使用一致的数据事实。

## D. 工程质量

- 无本次引入的未解释回归。
- 所有测试结果有记录。
- 浏览器测试实际执行。
- 截图来自真实运行页面。
- 性能测量可复现。
- 依赖和许可证明确。
- 文档与实际实现一致。

## E. 产品价值

最终必须能够回答：

> 与普通的课程文件列表、AI 摘要列表相比，这个知识地图为什么更值得学生使用？

答案必须来自实际功能和体验，例如：

- 跨材料融合。
- 真实知识关系。
- 来源追溯。
- 更快的知识定位。
- 更好的课程结构理解。
- 更高效的复习路径。

如果最终只有漂亮的节点和动画，却没有这些价值，任务仍然不合格。

# 二十五、严格禁止的捷径

1. 禁止跳过设计研究。
2. 禁止只看指定网站首页就宣称完成研究。
3. 禁止只调 CSS 就宣布重设计完成。
4. 禁止只展示静态截图而不运行交互原型。
5. 禁止默认所有节点全部展开。
6. 禁止将完整知识正文塞进节点。
7. 禁止通过缩小全图解决布局问题。
8. 禁止使用随机坐标或固定列索引伪装自动布局。
9. 禁止为了美观删除真实节点。
10. 禁止隐藏困难的知识关系。
11. 禁止把测试数据混入真实课程。
12. 禁止改变后端语义来迎合前端布局。
13. 禁止无依据地引入大量依赖。
14. 禁止复制受限制的付费组件源码。
15. 禁止只测模拟数据，不测真实课程。
16. 禁止把静态 DOM 测试当成真实浏览器验收。
17. 禁止编造性能数字。
18. 禁止将历史失败归咎于本次改动而不核对基线。
19. 禁止仅凭自动化测试通过就宣布产品体验优秀。
20. 禁止把未完成的项目写成 PASS。

# 二十六、最终报告格式

创建：

`reports/knowledge-map-premium-final-report.md`

必须包含：

1. Executive Summary。

3. 六个指定网站的实际研究结果。
4. 开源知识地图项目的研究结果。
5. 技术路线比较与最终选型。
6. 最终产品设计方向。
7. Design System。
8. 信息架构与核心用户流程。
9. 地图、列表、材料视图的实现。
10. 知识与证据追溯。
11. 依赖和许可证。
12. 数据完整性检查。
13. 自动化测试结果。
14. 真实浏览器验收结果。
15. 视觉评审与整改记录。
16. 性能结果。
17. 无障碍与响应式检查。

最终结论只能是：

- `PARTIAL`：核心功能完成，但仍有重要未验证项或缺陷。
- `BLOCKED`：因明确的外部或技术原因无法完成关键任务。

每个未验证项目必须写 `NOT VERIFIED`，不能通过文字包装成完成。

# 二十七、执行要求

现在开始：

**第一步：审计当前实际项目。**

然后按照 M0 → M8 推进。

不要在审计之前假设技术路线。

不要在设计研究之前开始大规模编码。

不要把整个任务简化成一个巨大的代码生成操作。

如果遇到需要选择的重大产品方向，先把证据、方案和代价记录下来，再做决定。

不需要因为 Token、时间或合理的开发成本而刻意缩减研究和验证。

如果一个成熟开源项目能显著提高最终质量，就认真评估并使用它；如果某种设计更适合本产品，即使需要重构前端，也可以采用。

最终目标是交付一个真正成熟的学习产品，而不是完成一份看起来很长的开发任务清单。

**核心原则：**

> Research deeply. Design deliberately. Build properly. Test in the real browser. Refine until the product is genuinely good.

> 先保证知识结构可理解，再保证知识关系可探索；先保证阅读体验，再追求视觉表现；先保证真实数据和真实交互，再宣布完成。
