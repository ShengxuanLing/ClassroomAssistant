## P0 — 明确的功能缺陷

### P0-1 顶栏「复习中心」是死链

**证据**

- `src/web/index.html:28` → `<a href="#/review-center" data-i18n="nav.reviewCenter">复习中心</a>`
- `src/web/app.js:812` → `else if (parts[0] === 'review-center' && parts.length === 2)`
- 求解结果：`#/review-center` 的 `parts = ['review-center']`，`length === 1` → 落到末尾 `else` → 「未找到页面」

**影响**：顶栏 12 项里唯一一个点下去必错。用户以为功能坏了。

**为什么没被测出来**：`app.js:685` 的 `markActiveNav` 归属表把 `#/review-center` 声明为属于路由 `#/review-center/<c>`，而 `index.html` 的 href 写的是 `#/review-center`。归属表测的是**高亮**，不是**可达性**，所以两边不一致不会被抓。

**建议修法**（二选一）

1. 让 href 带课程：`href` 由 JS 在 `loadSidebar()` 之后改写为 `#/review-center/<state.courseId>`；
2. 或在 `route()` 里加分支：`else if (parts[0] === 'review-center' && parts.length === 1) await pageCourseReview(await requireCourse());`

推荐 (2)：和 `#/learn`（`app.js:802` 用 `await requireCourse()`）的既有写法一致，不引入"href 被 JS 改写"这种隐式约定。

**配套测试建议**：加一条静态断言 —— `index.html` 里每个 `href="#/..."` 都必须能被 `route()` 的某个分支接住。这条能把整类死链一次性锁死（见 P0-2 也属这一类）。

### P0-2 错题本「详情」链接参数错位 → 打开的是错误页

**证据**

- 链接生成：`src/web/views/mistakes.js:319`
  ```js
  '<a href="#/mistakes/' + encodeURIComponent(row.knowledge_id) + '">'
  ```
  只生成**一段**（knowledge_id）。
- 路由接收：`src/web/app.js:816`
  ```js
  else if (parts[0] === 'mistakes' && parts.length === 2) await pageMistakeDetail(parts[1], parts[2]);
  ```
  `parts[2]` 在 `length === 2` 时恒为 `undefined`。
- 函数签名：`src/web/views/mistakes.js:333` → `pageMistakeDetail(courseId, knowledgeId)`
- 于是实际调用是 `pageMistakeDetail(<knowledge_id>, undefined)`。
- 同一文件的头注释 `mistakes.js:2` 写的是 `#/mistakes/<course>/<kp>` —— **注释、链接、路由三者互不一致**。

**实测（起真实服务，端口 8801，只读）**

```
GET /api/knowledge?course_id=course-32dde014868219be  -> 200, 61 个知识点
  第一个知识点 knowledge_id = aikp-06d64f6880f7bf61

GET /api/students?course_id=aikp-06d64f6880f7bf61
  -> 404
  {"error":{"code":"NOT_FOUND","message":"course 'aikp-06d64f6880f7bf61' not found"}}

GET /api/students?course_id=course-32dde014868219be
  -> 200, students=1        （对照：用真实 course_id 是正常的）
```

**影响**：错题本里每个知识点行末的「错题详情」点进去都是 `renderError` → 「请求失败 · NOT_FOUND」错误页。这是 Task 65 的核心页面之一，目前等于不可达。

**建议修法**：`mistakes.js:319` 的 href 补上课程段，与路由对齐：

```js
'<a href="#/mistakes/' + encodeURIComponent(courseId) + '/' +
  encodeURIComponent(row.knowledge_id) + '">'
```

`pageMistakes()` 的签名里已经有 `courseId`，不需要额外取数。

### P0-3 「处理」材料后，自动 AI 分析面板不显示

**证据**

- `src/web/views/students.js:398-431` `actionProcessMaterial()`：
  ```js
  } finally {
      button.disabled = false;
      route();              // ← 未 await
  }
  try {
      await loadAiSummaryIntoPanel(courseId, materialId);   // ← 此时面板已不存在
  } catch (err) { void err; }
  ```
- `src/web/app.js:790-794` `route()` 的第一件事是 `showLoading()`，它是**同步**执行 `setView()` 的 → `#view` 立刻被替换成加载卡，`#ai-panel` 随之消失。
- `src/web/views/materials.js:212-214` `loadAiSummaryIntoPanel()` 开头是：
  ```js
  const panel = document.getElementById('ai-panel');
  if (!panel) return;      // ← 必然命中
  ```
- 时序：`route()` 同步跑到第一个 `await`（`showLoading()` 之后）时 `#ai-panel` 已不存在；紧接着 `loadAiSummaryIntoPanel()` 取 DOM 拿到 `null` → **确定性早退**，不是概率性竞态。

**对照**：同一个 bug 在 `actionAiAnalyze` 里是对的 —— `src/web/views/materials.js:255` 写的是 `await route();`。代码注释（`materials.js:252-253`）自称 TASK-77 修掉了「报告闪一下就没」，但**只修了手动分析那一处，漏了自动分析这一处**。

**影响**：点「处理」→ toast 会说 AI 分析完成，但材料页下方的 AI 面板始终是空的。用户以为分析失败。

**建议修法**：`students.js:422` 改成 `await route();`（与 `materials.js:255` 对齐）。`actionRetryMaterial`（`:444`）、`actionProcessSession`（`:506`）虽然也 fire-and-forget，但它们后面没有依赖 DOM 的后续动作，属于可接受；若要统一，建议全部 `await`。

## P1 — 一致性与能力缺口

### P1-1 同一条「真相轴」在三个页面有三套标签

后端有两条独立真相轴（`validation_status` / `review_status`），UI 上三处写法不同：

| 页面 | 写法 | 用户看到（中文界面） |
|---|---|---|
| 我的课程 `views/dashboard.js:419-429` | `t('val.supported')` / `t('rev.confirmed')` | 证据已支持 / 人工已确认 |
| 复习中心 `views/review.js:222-231` | `stat('supported', …)` 裸字符串 | **supported / unverified / conflicted / pending / confirmed / rejected / kept_unverified** |
| 课程页 `views/courses.js:147-150` | `kv(t('已验证'),…)` 但 `kv('unverified',…)` | 已验证 / **unverified / conflicted / review pending** |

另外 `views/review.js:240` 与 `:262` 的表头也是裸英文：

```
'<th class="num">supported</th><th class="num">unverified</th><th class="num">conflicted</th>'
```

**现成可复用的 key 已经在表里**（`i18n.js:348-354`，三语齐全）：

```
val.supported / val.unverified / val.conflicted
rev.confirmed / rev.pending / rev.rejected / rev.kept_unverified
```

**影响**：切到 es / ca 界面时，复习中心和课程页会留一片英文枚举名；同一概念在两个页面显示成不同词，用户会以为是两个不同的指标。

**建议修法**：把 `mcAxisLabels()`（`dashboard.js:419`）提到公共位置复用，或把裸字符串换成上面这组 key。注意 `dashboard.js:405-418` 的注释已经解释了为什么**不能**用 `'val.' + key` 拼前缀 —— 复习中心这几处应当逐个字面写 key，与该注释的结论一致。

### P1-4 首屏没有「创建课程 / 创建课堂」入口 —— 新用户第一道墙

**证据**

前端所有写请求（`grep "method: 'POST'"`）只打这些路径：

```
/materials            /students              /answers
/learning/*           /reviews/*             /exercise-generation/*
/materials/*/process | /retry | /ai-analyze  /sessions/*/process
```

后端已注册但前端**从未调用**：

```
POST   /api/courses                  ← 建课程
POST   /api/sessions                 ← 建课堂
PATCH  /api/courses/{course_id}      ← 改课程信息
```

**前端自己承认了这一点**：

- `views/dashboard.js:14-15`，零课程时的空态直接把 curl 命令教给用户：
  ```
  POST /api/courses  {"name": "..."}
  POST /api/sessions {"course_id": "...", "session_number": 1}
  POST /api/materials (multipart) ?course_id=...&session_id=...
  ```
- `views/materials.js:55-57` 上传表单里课堂选择器为空时提示「还没有课堂。」，而注释（`:55-56`）写明「课堂目前只能通过 POST /api/sessions 创建」。

**影响**：新用户拿到这个应用，网页上**无法开始使用** —— 必须先用 curl 建课。项目历史上已经修过两次同类问题（`students.js:28-29` 的注册表单「永远渲染」、`materials.js` 的上传表单），课程/课堂是剩下的一处。

**建议修法**：在「我的课程」页（`#/courses`）加一张「新建课程」表单（`name` / `code` / `language` 三个字段，对应 `POST /api/courses`）；在课程页（`#/courses/<id>`）的课堂表上方加「新建课堂」（`session_number` / `title` / `date`，对应 `POST /api/sessions`）。两条都已注册，前端只需接线。

## P2 — 可访问性与视觉

### P2-1 深色模式下三处文字对比度不达 WCAG AA

按 WCAG 2.1 相对亮度公式实测（`styles.css` 的变量取值）：

| 位置 | 前景 / 背景 | 对比度 | 判定 |
|---|---|---|---|
| `.stepper li.done::after`（对勾） | `#fff` on `--ok #6ede9f` | **1.67:1** | FAIL（AA 需 4.5） |
| `button.primary` | `#fff` on `--accent #7aa7ff` | **2.39:1** | FAIL |
| `.brand-mark` | `#fff` on `--accent #7aa7ff` | **2.39:1** | FAIL |
| 对照：同一处在浅色模式 | `#fff` on `#167a4a` / `#2f6fed` | 5.36 / 4.55 | OK |

（深色模式的 pill 文字、正文、muted 全部合格：8.10 / 13.38 / 6.95 / 7.66。）

**根因**：深色模式把 `--ok` / `--accent` 调成了**浅色**（为了在深底上当文字色用），但 `.dot` / `button.primary` / `.brand-mark` 仍然假设这两个变量是**深色**底，于是白字压在浅底上。

**建议修法**：给"当背景用"的场景单独开变量，例如新增 `--on-accent`（深色模式下取 `#16181c` 一类的深色），把 `button.primary` 的 `color`、`.brand-mark` 的 `color`、`.stepper li.done::after` 的 `color` 都换成它。**不要**改 `--accent` 本身 —— 它还当着文字色（`a { color: var(--accent) }`）用，改深了链接就看不见了。

### P2-2 24 个表格全部缺 `scope="col"` 与 `<caption>`

扫描结果（`<table>` 计数 / `scope="col"` / `<caption>`）：

```
dashboard.js  4 / 0 / 0        review.js     4 / 0 / 0
courses.js    6 / 0 / 0        students.js   4 / 0 / 0
mistakes.js   3 / 0 / 0        knowledge.js  1 / 0 / 0
materials.js  1 / 0 / 0        exercises.js  1 / 0 / 0
```

**影响**：屏幕阅读器无法把单元格与列头关联。这些表列数多（课程页的课堂表 8 列、错题表 7 列），无 `scope` 时逐格朗读会失去上下文。

**建议修法**：`<th>` 统一加 `scope="col"`（纯机械改动，可脚本化）；`<caption>` 用 `<caption class="sr-only">` 的形式补上表名。

### P2-3 破坏性动作没有二次确认

- `grep "confirm("` 在 `src/web/` **零命中**。
- 「拒绝」（`views/knowledge.js:214` `data-action="review-reject"`）会直接改人工审核状态，`actionReview`（`students.js:510`）点下即 POST。
- 同类还有「整堂处理」（`courses.js:108/201`）与「重试」（`materials.js:34`、`courses.js:248`）。

**影响**：「拒绝」是审核轴上的终态之一，误点之后要人工再确认回来。而它和「确认」并排在同一行 `.actions` 里，间距只有 8px。

**建议修法**：至少给 `review-reject` 加一次 `confirm()`；更好的做法是把它和「确认」在视觉上分开（`button.danger` 已经有样式，但位置没分开）。

### P2-4 两处 `aria-label` 硬编码英文，不进 i18n

- `src/web/index.html:38` → `<select id="course-switch" aria-label="Course">`
- `src/web/index.html:42` → `<select id="ui-language" aria-label="UI language">`

**影响**：屏幕阅读器在 es / ca 界面下读出英文。项目对界面文案的三语一致性要求很高（有专门测试），这两处是漏网的。

**建议修法**：改成 `data-i18n-aria` 之类的钩子，或直接在 `applyI18n()` 里按 `state.lang` 设置。

## P3 — 性能、信息架构、可恢复性

### P3-1 每次导航 6 个**串行**请求

`route()`（`app.js:790`）的执行顺序：

```
showLoading()
→ await loadChrome()      → GET /health            (1)
→ await loadSidebar()     → GET /courses           (2)
                          → GET /course-selection  (3)
→ await pageXxx()         → GET /materials         (4)
                          → GET /sessions          (5)
                          → GET /processing        (6)
```

- `/health` **每次 hashchange 都重拉**（`app.js:796` 无条件调用 `loadChrome()`），但它只在启动 / ASR-OCR 模式变化时才有信息量。
- `loadChrome()` 与 `loadSidebar()` 互不依赖，可以 `Promise.all`。
- `pageMaterials` 的三个请求（`materials.js:9 / 12 / 18`）互不依赖，也可以并行。

本机延迟低，体感不明显；但这是"每次点导航都要串 6 次"的结构性开销，且 `#/dashboard` 在大课程上本来就不快（`app.js:718-720` 的注释自己提到了这点）。

**建议**：`await Promise.all([loadChrome(), loadSidebar()])`；`/health` 加一个"只拉一次"的标志位；材料页三个请求并行。

### P3-2 长任务不可恢复（刷新即丢失全部进度信号）

- `app.js:175` → `const tasks = []` 只在内存；`app.js:181` 还只保留最近 5 条。
- 服务端的处理是**同步**的（`POST /api/materials/{id}/process` 处理完才返回），音频转写可能持续数分钟。
- 用户在等待期间按 F5：任务坞清空，而服务端仍在跑。用户没有任何信号，只能回材料页看状态列。
- `GET /api/processing/{material_id}`（`endpoints.py:429`）已存在，天然适合做轮询，但前端没接。

### P3-4 动态 i18n key 是已知风险，且测试抓不到新增枚举

7 处 `t('前缀.' + 变量)`：

`app.js:85-88` 的注释自己写明了这个模式的后果：

> 拼前缀时后端新增一个码而前端没加文案，`t()` 会**原样返回 key**（页面上多出一个 `warn.XXX`），没有异常、没有日志；静态 i18n 检查也抓不到。

**建议**：让取值域从后端常量导入（而不是在测试里手抄），或对这几个前缀改成逐个字面写 key（与 `dashboard.js:405-418` 的结论一致）。至少把 `rs.block.` / `rs.reason.` / `learn.excluded.` 的取值域与后端常量做一次一致性断言。

### P3-5 `renderError` 里有两处 `t(t(...))` 双层调用

### P3-6 `pageExercise` 的学生来自全局 localStorage，跨课程会串学生
