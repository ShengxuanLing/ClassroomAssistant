## 候选路线

### A. 继续使用现有渲染技术，重做视图模型和交互

- 含义：保留零构建 Vanilla JS + SVG/HTML，重新实现 View Model / 布局 / 交互 / 五个工作视图。
- 优势：
  - 零新前端依赖，兼容现有加载顺序与门禁。
  - 文字天然可选中/可访问，渲染可控。
  - 可直接复用现有 i18n、空态、错误态模式。
- 缺陷：
  - 布局质量、边路由、拟合、中心化、关系边可读性都要靠自研把控。
  - 大图/密集关系的天花板取决于投入。
- 适合场景：保持极简依赖，且愿意在设计/原型/验收上花足够时间。

### B. 采用 React Flow / XYFlow + 合适的布局引擎

- 优势：自定义节点、编辑交互、视口控制、MiniMap/Controls 等开箱能力较强，社区成熟。
- 缺陷：React 优先生态，与当前 Vanilla 栈不直接兼容；自动布局不内置；密集语义边可读性仍需验证；依赖/加载方式的门禁影响需单独验证。
- 适合场景：愿意引入 React 图栈，以节点卡片式界面和折叠/局部视图为核心目标。

### C. 采用更适合当前目标的图形引擎

- C1 Cytoscape.js：图模型/查询/分析强，适合关系探索与邻居展开，但卡片式课程节点 UI 需自建。
- C2 AntV G6：布局/交互/渲染选择丰富，适合把关系探索做成一等能力；需实测课程数据下的可读性与性能。
- C3 Mind Elixir / jsMind：层级/编辑/展开状态开箱可用，但混合语义关系图能力较弱；不应误判为通用图编辑器。

## 推荐路线（初步）

先做最小可行研究 PoC，再锁死技术路线。

### 如果目标是最小依赖 + 可控阅读体验

首选 **A + 成熟布局参考**：沿用零构建 Vanilla JS，但不从零闭门造车； borrow 已验证的层级/折叠/搜索/聚焦模式，并在原型阶段用真实课程数据逼真检验可读性。

### 如果关系探索/大图导航是不可妥协的核心

再认真评估 **B 或 C2**，并接受技术栈/加载方式变化带来的成本。选哪个再由真实课程数据上的交互与性能 PoC 决定，而不是凭“看起来漂亮”选。

### 哪个路线不建议轻易选

- 不建议为了“高级感”而选通用白板类控件作为主画布。
- 不建议把纯思维导图控件当成混合关系图的完整方案。
- 不建议未经真实课程数据验证，就把密集语义边默认展示为默认视图。

1. 实测 `GET /courses/<真实课程 id>/knowledge-map` 是否存在，返回结构是否可直接投影为课程→主题→知识点。
2. 实测真实课程的知识点/主题/关系/材料/证据/合并建议数量，确认规模与密度。
3. 核查残留的 V2 `km.*` i18n 键与任何残留引用，避免误删尚有消费者的键。
4. 确定是否接受前端技术栈变化（如引入 React 图栈），或坚持零构建 Vanilla 栈。
5. 用同一份真实数据对候选画布（如 Cytoscape / G6 / 自研 SVG）做最小 PoC，至少验证层级折叠、聚焦邻居、搜索定位、默认初始视图是否可读。
